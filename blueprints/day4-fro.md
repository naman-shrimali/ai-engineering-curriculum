## fro-01 — Voice & Realtime AI

**Meta:** experimental/volatile · diff 3 · 180 min → 4,000–4,600 words (lean, hedged) · prereqs [api-04, api-05] · related [fro-02, api-04, agt-08]
**Thesis:** realtime voice systems are latency-budget engineering above all — every millisecond of the speech→understanding→response→speech loop is contended, and the architectural fork (cascaded STT→LLM→TTS vs speech-native models) is a trade between control/debuggability and latency/expressiveness.
**Sections:** (1) Intuition: conversation has a latency contract humans feel (~sub-second response, turn-taking, barge-in) — voice AI is api-05's latency discipline under a hard real-time deadline; the budget is the design. (2) The two architectures: cascaded pipeline (STT → LLM → TTS — modular, debuggable per stage, each an eval target; latency accumulates across stages) vs speech-native/realtime models (audio in, audio out — lower latency, more expressive, less controllable/inspectable; the api-04 "everything becomes tokens" applied to audio); the fork's trade table. (3) The latency budget decomposed: STT streaming (partial transcripts), LLM TTFT (api-05's caching/streaming pay hard here), TTS first-audio, network — and the techniques (streaming everything, speculative/eager response, endpointing); the barge-in/interruption problem (the user talks over the model — state management under interruption). (4) Turn-taking and dialogue state: endpoint detection (when did the user stop?), the interruption-and-resume problem (rag-01/agt-04 state under realtime constraints), and voice-specific UX (backchannels, latency-masking). (5) Production reality (fence hard — experimental): what works (scoped, turn-based, forgiving flows) vs what's hard (open-domain, noisy, high-stakes); evaluation of voice systems (WER for STT, but end-to-end task success and latency percentiles are the honest metrics — evl-01); the honest "this is moving fast" posture.
**Must land:** latency budget is the whole discipline (api-05 under a deadline); cascaded vs speech-native is control-vs-latency; barge-in/interruption is the hard state problem; streaming everywhere is mandatory; evaluate end-to-end, not just WER.
**Diagrams:** (1) *graph LR* both architectures side by side with per-stage latency annotations (cascaded vs native); (2) *sequenceDiagram* a turn with barge-in/interruption handling.
**Mini-project:** build a minimal cascaded voice loop (streaming STT → your capstone LLM route → streaming TTS); measure the end-to-end latency budget per stage; then break one stage's streaming and feel the degradation. Success: a working voice turn with a measured latency decomposition. Capstone: optional voice front-end to the capstone.
**Sources:** [T1] OpenAI Realtime API docs · [T1] a streaming STT/TTS provider's docs (exemplar) · [T2] a speech-LLM paper (e.g. Moshi arXiv:2410.00037 or current) · [T2] Whisper arXiv:2212.04356 (STT foundation) · [T4] a realtime-voice engineering post.
**Volatile fences:** the whole realtime-model landscape (heaviest); the latency-budget discipline and architecture fork are the durable layer. Lede leans hard on experimental status.

## fro-02 — Generative Media for Engineers

**Meta:** experimental/volatile · diff 2 · 120 min → 3,800–4,300 words (lean) · prereqs [api-04] · related [fro-01, api-04, sec-03]
**Thesis:** integrating image/video/audio generation into products is an engineering problem distinct from the models' internals — prompting/conditioning, async job orchestration (generation is slow), cost, moderation, and licensing/provenance — and the engineer's job is the integration, not the diffusion math.
**Sections:** (1) Intuition: generative media is a slow, expensive, moderation-heavy async tool call (api-03/prd-01's async pattern) — treat the model as a capability behind a job queue, and the engineering is the orchestration and governance around it. (2) Just-enough model literacy: diffusion in two paragraphs (iterative denoising — enough to reason about steps/latency/quality knobs, not to implement); the modality landscape (image mature, video/audio emerging — fence); conditioning mechanisms (text prompts, image references, control signals) as the product surface. (3) The integration engineering: async job orchestration (generation takes seconds-to-minutes — prd-01's queue worker, api-05's batch mindset), cost (per-generation pricing, the resolution/steps/quality dial), caching generated assets (derived data — eng-01's contract), and the prompting/iteration loop (evl-01 discipline — media quality is judge-or-human scored). (4) Governance (the load-bearing engineering, sec-03): content moderation (generation is a harm surface — CSAM/deepfake/IP, provider filters + your obligations, api-04/sec-02), licensing and provenance (who owns generated output? training-data IP questions? — the honest "consult counsel" + C2PA/watermarking provenance tech), and consent/likeness. (5) Production patterns: human-in-the-loop review for published media (the eng-02 gate, media edition), the async UX (generation progress, regeneration), and evaluation (aesthetic/faithfulness judging — evl-03 for media).
**Must land:** the engineering is orchestration + governance, not diffusion math; generation is a slow async tool (queue it); moderation and licensing/provenance are load-bearing (not afterthoughts); generated assets are derived data (cache them); human review gates published media.
**Diagrams:** (1) *graph LR* the generation pipeline: prompt/condition → async job → moderation → provenance-tag → cache → human review → publish.
**Mini-project:** integrate one image-generation API into an async pipeline: job queue, moderation check, provenance metadata, generated-asset cache, and a human-review gate; measure per-generation cost/latency. Success: a governed async generation pipeline (not just an API call). Capstone: optional media capability with full governance.
**Sources:** [T2] Ho et al., DDPM/diffusion, arXiv:2006.11239 (the two-paragraph literacy) · [T2] Rombach et al., latent diffusion, arXiv:2112.10752 · [T1] provider image/video-gen API docs (moderation, pricing) · [T1] C2PA content-provenance spec · [T4] a generative-media-in-production engineering post.
**Volatile fences:** the entire model/capability landscape (heavy); async-orchestration and governance engineering are the durable layer.

## fro-03 — On-Device & Edge AI

**Meta:** experimental/volatile · diff 3 · 120 min → 3,800–4,300 words (lean) · prereqs [api-07, ftn-06] · related [fro-02, api-07, prd-06]
**Thesis:** running models on-device (phone/browser/embedded) trades capability for privacy, latency, offline operation, and zero marginal cost — a deployment target where the api-07 memory math and ftn-06 distillation meet hard device constraints, and the capability floor (fnd-09) decides what's feasible.
**Sections:** (1) Intuition: on-device inverts the cloud assumptions — no network, fixed tiny memory, battery-bound compute, but data never leaves and latency is local; it's api-07's self-hosting taken to the smallest extreme. (2) Why on-device (the honest wins): privacy/data-residency (data never leaves the device — sec-03's strongest guarantee), offline operation, zero marginal cost, latency (no network hop); mapped to when each decides. (3) The constraints and the math: device memory classes (phone/browser/embedded — the api-07/fnd-05 memory math at 1–8GB budgets), quantization as mandatory not optional (prd-03/api-07 — 4-bit and below), the capability floor (fnd-09's bands for small models — what a phone-sized model reliably does, ftn-06's SLMs as the targets); the honest capability gap accounting. (4) The runtime landscape (fence hard): on-device frameworks (Core ML / ONNX Runtime / llama.cpp-on-mobile / WebGPU+WebLLM for browser — categories with exemplars), the format/conversion pipeline (train/distill → quantize → convert → deploy), hardware acceleration (NPUs/Metal/WebGPU); the "read current specs" posture. (5) The hybrid pattern (the pragmatic reality): on-device for the private/offline/fast path, cloud fallback for the hard tail (the eng-05 cascade across the device boundary — a small local model escalates to the cloud on low confidence, fnd-08); the deployment/update problem (shipping model updates to devices — prd-06's cold-start at the extreme).
**Must land:** on-device trades capability for privacy/latency/offline/cost (name the trade); quantization is mandatory (prd-03); the capability floor decides feasibility (fnd-09/ftn-06); hybrid local+cloud cascade is the pragmatic pattern; distillation (ftn-06) is the model-sourcing path.
**Diagrams:** (1) *graph TD* the on-device decision (privacy/offline/latency needs × capability floor → on-device / hybrid / cloud); (2) *graph LR* the hybrid cascade across the device/cloud boundary.
**Mini-project:** run a small quantized model on a real device (phone via an app framework, or browser via WebLLM); measure memory, latency, and quality on a capstone-relevant task vs the cloud route; design the hybrid cascade (what stays local, what escalates). Success: a model running on your own device with a measured capability/cost trade vs cloud. Capstone: an on-device or hybrid variant of a capstone route.
**Sources:** [T1] Apple Core ML docs · [T1] ONNX Runtime docs · [T1] WebLLM / MLC-LLM docs · [T1] llama.cpp mobile docs (reuse api-07) · [T2] reuse Dettmers QLoRA/int8 for the quantization floor · [T4] an on-device-LLM engineering post.
**Volatile fences:** the entire runtime/hardware landscape (heaviest); the trade-off logic, memory math, and hybrid pattern are durable.

## fro-05 — The AI Engineer Interview & Portfolio

**Meta:** evolving/mixed · diff 2 · 180 min → 4,300–5,000 words · prereqs [agt-01, rag-05, evl-01] · related [fnd-01, eng-12, fro-04]. **The curriculum's closing chapter — the career capstone; pairs with eng-12 (the drill index).**
**Thesis:** landing an AI engineering role is a portfolio-and-judgment game — the capstone you've built across this curriculum IS the portfolio, the interview types reward the mechanism-grounded thinking the chapters trained, and the differentiator is demonstrable eval/production judgment, not model trivia.
**Sections:** (1) Intuition: the field hires for judgment under uncertainty (fnd-09's jagged frontier) — can you build something real, know why it works, and know how you'd know it works (evl-01); the capstone thread is the evidence.
