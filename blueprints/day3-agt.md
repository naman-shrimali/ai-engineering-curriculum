## agt-01 — Agent Fundamentals

**Meta:** evolving/mixed · diff 3 · 240 min → 5,000–6,200 words · prereqs [api-03] · related [agt-02, agt-03, sec-01, eng-02]. **Widest-fan-out node in module 4 — give it weight.**
**Thesis:** an agent is api-03's tool round trip in a loop until done — build it from scratch, no framework, and you understand every reliability and security property that frameworks later hide; the model plans, your runtime acts.
**Sections:** (1) Intuition: the plan-act-observe loop; ReAct as the naming of the pattern (cite Yao); the crucial reframe — the model contributes decisions, the runtime contributes everything else (this is eng-02's spine, taught from first principles). (2) Build the minimal loop in code: while-loop over api-03 calls, appending tool results as messages, terminating on a final answer — ~40 lines; the reader should be able to reproduce it. Show the trajectory growing (context cost — rag-01/api-05 forward). (3) The loop's hidden requirements, discovered by breaking the minimal version: no termination (→ budgets), errors that crash vs inform (→ in-band errors), no memory of the plan (→ state), unvalidated actions (→ the control points, agt-02/eng-02 forward). (4) When to use an agent at all: the workflow-vs-agent decision (eng-05 #13) — fixed path → code the sequence; genuinely dynamic path → the loop; "most 'we need an agent' is a tool-design problem" (Anthropic's building-effective-agents lesson). (5) The reliability preview: why agents are hard (autoregressive error compounding — fnd-08 — over long horizons; each step multiplies failure probability) — motivating agt-09 without duplicating it.
**Must land:** build-from-scratch before frameworks (agt-07); the model/runtime split is the whole mental model; workflow-first discipline; trajectory growth is a first-order cost.
**Diagrams:** (1) *stateDiagram-v2* the minimal loop (subset of eng-02's, taught); (2) *graph TD* the workflow-vs-agent decision.
**Mini-project (capstone agent):** build the loop from scratch on the api-01 gateway with 2–3 tools (one being your rag-05 retrieval-as-tool); no framework; add a step budget; watch it solve a multi-step task and observe one failure mode. Success: a working agent you fully understand, line by line. Capstone: the agent that wraps the RAG capstone.
**Sources:** [T2] Yao et al., ReAct, arXiv:2210.03629 · [T4] Anthropic, "Building effective agents" · [T1] Anthropic/OpenAI tool-use docs (reuse api-03's) · [T2] Wang et al., survey on LLM agents, arXiv:2308.11432.
**Volatile fences:** none major; framework specifics deferred to agt-07.

## agt-02 — Tool Design

**Meta:** evolving/mixed · diff 3 · 180 min → 4,300–5,000 words · prereqs [agt-01] · related [agt-05, agt-08, eng-02]
**Thesis:** an agent's competence ceiling is its tools' quality — tool interfaces are prompts the model reads at decision time, so naming, schemas, descriptions, granularity, and error design are the highest-leverage agent work, and most "smarter agent" problems are "better tools" problems.
**Sections:** (1) Intuition: tools are the agent's API to the world, and the model chooses among them by *reading* — so tool design is prompt engineering (api-02/api-03 doctrine, applied). (2) Anatomy of a good tool: semantic name, description-as-instruction (when to use AND when not to), typed schema with enums/required-null (api-03), examples in the description; the model's-eye-view test (could you pick the right tool from descriptions alone?). (3) Granularity: too-fine (many calls, orchestration burden) vs too-coarse (model can't compose); designing for composition; the token cost of the catalog (every schema in every prompt — the eng-05 "30 tools, 3 used" story). (4) Error design: errors-in-band and *actionable* (the model must be able to recover — "order not found, try searching by email" beats a stack trace); idempotency at the interface (natural keys — the eng-05 pattern). (5) Tool catalogs at scale: route-scoping, overlap elimination (disjoint "use when" clauses), dynamic tool selection (retrieve relevant tools — forward to agt-05/MCP), versioning tools like APIs.
**Must land:** tool selection accuracy is a measurable metric, not a hope; descriptions are prompts (re-tune per model — api-02's rule); actionable errors are what make the loop recover; catalog size has a token AND an accuracy cost.
**Diagrams:** (1) *graph TD* good-vs-bad tool decision annotated (naming/desc/schema/errors); (2) small before/after table of a redesigned tool.
**Mini-project:** take your agt-01 agent's tools; measure tool-selection accuracy on 20 tasks; redesign the worst tool (name/description/schema/errors) and remeasure; add one overlapping tool and observe the confusion. Success: measured selection-accuracy delta from a description rewrite. Capstone: the capstone agent's tools, hardened.
**Sources:** [T1] Anthropic tool-use best-practices docs · [T1] OpenAI function-calling guide · [T4] Anthropic building-effective-agents (tool section) · [T2] reuse Schick Toolformer arXiv:2302.04761 (historical).
**Volatile fences:** none major.

## agt-03 — Reasoning & Planning

**Meta:** evolving/volatile · diff 4 · 240 min → 5,000–6,200 words · prereqs [agt-01, fnd-07] · related [agt-06, agt-09, fnd-08]
**Thesis:** test-time compute is a controllable resource — CoT, reasoning models, and explicit planning trade tokens for accuracy on hard problems, but the trade has a cost curve and a jagged payoff (fnd-09), so "how much should it think" is a routed product decision, not a default.
**Sections:** (1) Intuition: thinking = computation spent before committing (fnd-05: each token is a forward pass); the fnd-07 reasoning-model story recapped as the mechanism. (2) The spectrum: zero-shot CoT (prompt-elicited — cite Wei/Kojima; matters less on reasoning-trained models — the fnd-07 volatile note) → reasoning models with effort dials → explicit planning scaffolds (plan-then-execute) → search/tree methods (ToT — when the branching factor justifies the cost, which is rarely). (3) The cost/accuracy curve: reasoning tokens multiply latency and spend (the fnd-07 "paying for thought" example — 6× cost, route the hard 15%); measuring where thinking helps vs wastes (fnd-09's jaggedness — verifiable domains gain most). (4) Planning in agents: explicit plans as structured state (rag-01's survival contract — the plan must survive compaction, the eng-02 "changed its mind" failure); replanning on observation; plan-vs-react trade-offs. (5) The faithfulness caveat (fnd-07, sharpened): visible reasoning traces are trained output, not introspection — don't build logic that trusts the trace as ground truth; self-consistency (fnd-08) as the accuracy-buying tool where verification is cheap.
**Must land:** test-time compute is a dial that belongs in a router (prd-05/api-06 economics); reasoning-model presence changes prompting (don't hand-scaffold CoT on models that do it internally — check provider guidance); plans are state, not prose; traces aren't introspection.
**Diagrams:** (1) *graph TD* the reasoning-depth decision (task stakes × verifiability → effort level); (2) *graph LR* plan-then-execute vs react loops compared.
**Mini-project:** on a reasoning-heavy task set, compare standard vs reasoning-model vs self-consistency (n=5) — accuracy, tokens, latency each; build a router that sends only classifier-flagged-hard cases to expensive thinking. Success: the measured cost/accuracy curve + a working router. Capstone: the capstone agent routes reasoning effort.
**Sources:** [T2] Wei CoT arXiv:2201.11903 · [T2] Kojima zero-shot arXiv:2205.11916 · [T2] Wang self-consistency arXiv:2203.11171 · [T2] Yao Tree of Thoughts arXiv:2305.10601 · [T2] DeepSeek-R1 arXiv:2501.12948 (reasoning-RL, reuse from fnd-07) · [T1] provider extended-thinking/reasoning docs.
**Volatile fences:** reasoning-model capabilities and effort-control APIs churn fast — fence heavily; the compute-for-accuracy principle and routing discipline are stable.

## agt-04 — Agent Memory & State

**Meta:** evolving/mixed · diff 3 · 180 min → 4,300–5,000 words · prereqs [agt-01, rag-01] · related [agt-06, rag-05, eng-02]
**Thesis:** agents need state the context window can't hold — the rag-01 compaction ladder extended into persistent memory: working state (this task), short-term (this session), long-term (across sessions), each with a survival contract and a retrieval story.
**Sections:** (1) Intuition: the window is working memory (rag-01); everything durable lives outside it and is *fetched back* — memory is retrieval pointed at the agent's own history. (2) The memory hierarchy: working state (the structured plan/decisions region — rag-01's survival contract, re-pinned every step); short-term (session history — windowing/summarization at boundaries, cache-aware — api-05); long-term (cross-session: user preferences, learned facts, past task outcomes). (3) Long-term mechanics: store as structured facts vs raw episodes; retrieval over memory (rag-05 machinery pointed inward — embeddings over past interactions); write policy (what's worth remembering — the hard problem; over-remembering rots, under-remembering forgets). (4) State as data not prose (the eng-02 "changed its mind" failure resolved): decisions/constraints/progress as explicit typed state, survivable across compaction; the difference between context (transient) and memory (persistent). (5) Multi-agent state (agt-06 forward): shared vs isolated memory, the handoff problem.
**Must land:** memory = retrieval over own history; state-as-data beats state-as-history; the survival contract governs all three tiers; write policy is the under-appreciated hard part.
**Diagrams:** (1) *graph TD* the memory hierarchy (working/short/long) with retrieval + write paths; (2) *stateDiagram-v2* compaction-with-survival-contract across a session.
**Mini-project:** add persistent memory to the capstone agent: structured working state + session summarization + a long-term store (user facts) retrieved at task start; test cross-session recall and one over-remembering failure. Success: an agent that remembers the right things across sessions and you can show what it forgot on purpose. Capstone: the capstone agent gains memory.
**Sources:** [T2] Park et al., Generative Agents (memory stream), arXiv:2304.03442 · [T2] Packer et al., MemGPT, arXiv:2310.08560 · [T4] Anthropic context-engineering post (reuse from rag-01) · [T2] reuse Liu lost-in-the-middle for the why-not-just-keep-everything.
**Volatile fences:** memory-framework tooling; the hierarchy and survival-contract doctrine are stable.

## agt-05 — Model Context Protocol (MCP)

**Meta:** evolving/volatile · diff 3 · 180 min → 4,300–5,000 words · prereqs [agt-02] · related [agt-06, agt-08, sec-01, eng-09]
**Thesis:** MCP standardizes how agents discover and call tools/resources across vendors — the "USB-C for tools" — turning agt-02's bespoke tool integrations into a reusable ecosystem, while inheriting agt-02's design burden and adding a supply-chain security surface.
**Sections:** (1) Intuition: before MCP, every app × every tool was a custom integration (N×M); a protocol makes it N+M (the historical driver). (2) Architecture: client/server model, the primitives (tools, resources, prompts), transport, capability negotiation — enough to reason about it, teach from the spec (T1). (3) What it changes for the engineer: consuming MCP servers (instant tool ecosystems) vs authoring them (exposing your systems as tools — agt-02's design rules apply unchanged; a well-designed MCP tool is still a well-designed tool). (4) The security surface (sec-01/eng-09 forward, load-bearing): MCP servers are supply chain — provenance, pinning, credential scoping per server; tool descriptions from third-party servers are injection carriers; the confused-deputy risk of an agent wiring together tools across trust boundaries. (5) The ecosystem reality (fence hard — volatile): adoption is real and moving fast; the durable knowledge is the N×M→N+M value and the tool-design-still-matters lesson, not the current server catalog.
**Must land:** MCP is plumbing that doesn't fix tool design (agt-02 still applies); servers are supply chain (eng-09 rule); N+M is the durable value; consume vs author are different jobs.
**Diagrams:** (1) *graph TD* N×M integrations vs N+M via protocol (the value prop); (2) *sequenceDiagram* client ↔ MCP server capability negotiation + tool call.
**Mini-project:** author a minimal MCP server exposing one of your capstone tools; connect it to an MCP-capable client; then consume one third-party server and audit its tool descriptions for injection surface. Success: your tool reused across a protocol boundary + a security observation. Capstone: capstone tools exposed via MCP.
**Sources:** [T1] Model Context Protocol specification (modelcontextprotocol.io) · [T1] Anthropic MCP docs · [T2] Greshake indirect-injection arXiv:2302.12173 (supply-chain risk, reuse) · [T4] a current MCP ecosystem writeup (select at generation).
**Volatile fences:** ecosystem/adoption/server catalog — heavy; protocol shape and security doctrine are stable.

## agt-06 — Multi-Agent Systems

**Meta:** evolving/volatile · diff 4 · 240 min → 5,000–6,200 words · prereqs [agt-04] · related [agt-07, agt-09, eng-02]
**Thesis:** multiple agents beat one only when context isolation or parallelism genuinely pays — the burden of proof is on the topology, because coordination adds failure modes (information loss at handoffs, compounding errors, cost multiplication) that a well-designed single loop avoids.
**Sections:** (1) Intuition: the eng-02 orchestration ladder, taught — single loop → workflow → subagents → topologies, each rung earning its place by measured failure of the previous. (2) When multi-agent actually pays: context isolation (each subagent's window stays clean — the real win, cite Anthropic's multi-agent research post honestly including its cost findings), parallelism (independent subtasks), specialization (distinct tool sets/prompts). (3) The patterns: supervisor/orchestrator-worker (a coordinator delegates bounded subtasks — the workhorse), pipeline (fixed handoff sequence — often better as a workflow, eng-05 #13), and the honest treatment of swarm/debate patterns (intellectually interesting, rarely production-justified). (4) The coordination tax: information loss at handoffs (each boundary is lossy — agt-04's state problem across agents), error compounding across agents (fnd-08 at system scale), cost multiplication (N agents × trajectories — the api-05/prd-05 arithmetic; Anthropic reports multi-agent token use far above single-agent), debugging difficulty (whose trajectory failed?). (5) The decision framework: default single-agent; adopt multi only with a named win (isolation/parallelism/specialization) that a single loop provably can't deliver.
**Must land:** burden of proof on the topology; context isolation is the strongest real justification; coordination is a tax not a feature; most multi-agent should be workflows or subagents, not peer topologies.
**Diagrams:** (1) *graph TD* the topology catalog (single/supervisor/pipeline/swarm) with when-to-use; (2) *graph LR* the coordination-tax accounting.
**Mini-project:** take a capstone task and build it two ways — single agent vs supervisor+subagents; measure quality, tokens, latency, and debuggability; find the one dimension multi-agent wins (or prove it doesn't for your task). Success: an evidence-based single-vs-multi decision. Capstone: capstone stays single-agent unless the evidence says otherwise (a valid, common outcome).
**Sources:** [T4] Anthropic, "How we built our multi-agent research system" (isolation win + cost findings) · [T4] Anthropic building-effective-agents (orchestrator-worker) · [T2] agent survey arXiv:2308.11432 (reuse) · [T2] a current multi-agent framework paper (e.g. AutoGen, arXiv:2308.08155).
**Volatile fences:** framework/topology fashion; the coordination-tax and burden-of-proof doctrine are stable.

## agt-07 — Agent Frameworks Landscape

**Meta:** evolving/volatile · diff 2 · 180 min → 4,000–4,600 words (lean, volatile) · prereqs [agt-01] · related [agt-06, eng-05, api-06]
**Thesis:** frameworks trade control for convenience — having built the loop from scratch (agt-01), you can judge which abstractions help and which hide the properties you need to control; the selection procedure (api-06 bake-off) applies, and "no framework" is a legitimate, common answer.
**Sections:** (1) Intuition: frameworks are opinions about the eng-02 architecture — some own the loop, some own orchestration, some own observability; the question is which opinions match your needs. (2) The category map (fence volatile, teach as categories with current exemplars): loop/orchestration frameworks (LangGraph-class — graph-based control), provider agent SDKs (Claude Agent SDK, OpenAI Agents SDK — closest to the raw loop), higher-level harnesses. (3) The evaluation axes: control granularity (can you reach the five control points? — eng-02), observability (does it emit traces? — evl-04), state model (agt-04), lock-in vs portability (api-06's migration-cost logic), and the "does it hide what you need to see" test. (4) The no-framework case: for a well-understood loop, raw + your gateway (api-01) is often clearest — frameworks earn their place at orchestration complexity, not at hello-world. (5) Selection as bake-off: the api-06 procedure applied — prototype the same task in 2 candidates + raw, evaluate on control/observability/velocity, decide with a log.
**Must land:** you built it from scratch first for exactly this judgment; frameworks hide control points (audit for that); no-framework is legitimate; selection is a bake-off, not a popularity contest.
**Diagrams:** (1) *graph TD* the selection decision (control needs × orchestration complexity → framework category or none).
**Mini-project:** reimplement your agt-01 agent in one framework; diff the code; audit whether you can still reach all five eng-02 control points; write the api-06-style decision. Success: an evidence-based framework/no-framework decision for the capstone. Capstone: capstone framework choice, justified.
**Sources:** [T1] LangGraph docs · [T1] Claude Agent SDK docs · [T1] OpenAI Agents SDK docs · [T4] a current framework-comparison engineering post (select at generation). All heavily volatile — flag.
**Volatile fences:** the entire landscape; only the evaluation axes and "build-first-then-judge" are stable. Lede must lean hard on this.

## agt-08 — Computer Use & Browser Agents

**Meta:** experimental/volatile · diff 4 · 180 min → 4,000–4,600 words (hedged, experimental) · prereqs [agt-02, api-04] · related [agt-09, sec-01, eng-09]
**Thesis:** agents that operate GUIs/browsers via screenshots + synthesized actions are tools-all-the-way-down (agt-02) with a vision loop (api-04), unlocking systems without APIs — at a reliability and security cost that keeps them frontier, not routine.
**Sections:** (1) Intuition: when there's no API, the UI is the API — screenshot → reason → click/type → screenshot (the loop, api-04 vision + agt-01 loop combined). (2) Mechanics: the perception-action cycle, coordinate grounding (the hard vision problem — api-04's precision shallows bite here), action spaces, the latency reality (each step = screenshot + vision-prefill + reasoning — slow by construction, fnd-05). (3) The reliability envelope (honest, experimental): what works (structured, forgiving, human-supervised flows) vs what doesn't (precise, high-stakes, unattended); error recovery when the UI changes under you. (4) The security surface (load-bearing — sec-01/eng-09/api-04 injection): the screen is untrusted input, a malicious page/banner injects instructions through pixels (api-04's screenshot-agent example), and the action space is powerful — least privilege and human gates (eng-02) are non-negotiable; the "agent with a browser and your credentials" threat. (5) Where it's heading: fence hard — this is the most experimental chapter in the module; teach the loop structure and the risk model, not current capability claims.
**Must land:** UI-as-API is the unlock; precision grounding is the reliability ceiling (api-04 shallows); the screen is an injection surface; human gates + least privilege mandatory; experimental status is honest.
**Diagrams:** (1) *stateDiagram-v2* the perception-action loop with the injection + gate points marked.
**Mini-project:** with a computer-use-capable model on a sandboxed VM, automate one simple multi-step GUI task; log the failure rate over 10 runs; then run the injection test (a page instructing the agent) and verify your gates hold. Success: a measured reliability rate + a survived injection test. Capstone: optional — most capstones won't need this; note that.
**Sources:** [T1] Anthropic computer-use docs · [T2] a current GUI-agent benchmark paper (e.g. WebArena arXiv:2307.13854, OSWorld arXiv:2404.07972) · [T2] Bagdasaryan image-injection arXiv:2307.10490 (reuse from api-04) · [T4] current computer-use engineering post.
**Volatile fences:** capability claims — heaviest in the module; loop structure and risk model are the durable layer.

## agt-09 — Agent Reliability & Evaluation

**Meta:** evolving/mixed · diff 4 · 240 min → 5,000–6,200 words · prereqs [agt-01, evl-03] · related [agt-06, evl-05, eng-02, eng-07]. **The chapter that makes agents shippable — treat as module 4's evl-01.**
**Thesis:** agents fail differently than single calls — over long horizons, errors compound and the failure surface is the whole trajectory — so reliability demands trajectory-level evaluation, failure taxonomies, and human-in-the-loop gates, turning demos into products.
**Sections:** (1) Intuition: the demo-quality trap (fnd-01) is worst for agents — a 90%-per-step agent is 35% over 10 steps (0.9^10); reliability is the multiplicative-decay problem. (2) Trajectory evaluation (the core skill, extends evl-01/evl-03 to sequences): scoring not just the final answer but the path — did it use the right tools, recover from errors, avoid wasteful loops; per-step vs end-to-end metrics; trajectory eval cases (the eng-02 trajectory log as eval source — eng-03's flywheel for agents). (3) The failure taxonomy (agent-specific, extends fnd-09): wrong tool / hallucinated arguments / no recovery from errors / infinite or repetitive loops (fnd-08's repetition at task scale) / context rot over long trajectories (rag-01) / plan abandonment (agt-04) / budget exhaustion — each with detection. (4) Human-in-the-loop as design (eng-02/eng-05 #14): the privilege-tier table as reliability infrastructure, confirmation gates on consequential actions, escalation-on-uncertainty, the trajectory-attached handoff. (5) Making agents production-ready: the reliability checklist (budgets, idempotency, gates, stall detection, trajectory logging — synthesizes eng-02 into a launch gate), staged autonomy (supervised → semi → auto as evidence accrues), and the honest bar: agents ship when their failure is *contained*, not when it's eliminated.
**Must land:** multiplicative decay is the core math (compute 0.9^n); trajectory eval ≠ final-answer eval; the failure taxonomy is the debugging vocabulary; human gates are reliability infrastructure not UX friction; contained failure is the shipping bar.
**Math that earns its place:** per-step reliability → end-to-end (0.9^n table); expected steps to failure. This is the chapter's signature number.
**Diagrams:** (1) *graph TD* the agent failure taxonomy → detection → mitigation; (2) a small table of per-step vs end-to-end reliability at n steps.
**Mini-project:** build a trajectory eval for the capstone agent: 20 task cases scored on path quality (judge — evl-03) + outcome; catalog its top-3 failure modes from real trajectories; add a human gate on the one consequential action and stall detection. Success: measured trajectory pass-rate + the 0.9^n decay observed in your own agent. Capstone: the capstone agent becomes shippable; feeds eng-12 interview stories.
**Sources:** [T4] Anthropic building-effective-agents (reliability) + multi-agent post (eval) · [T2] Zheng judge arXiv:2306.05685 (trajectory judging) · [T2] a current agent-benchmark paper (e.g. τ-bench arXiv:2406.12045, SWE-bench arXiv:2310.06770) · [T2] Yao ReAct (reuse) · reuse fnd-08 for compounding.
**Volatile fences:** benchmark specifics; the decay math, taxonomy, and gate doctrine are stable.
