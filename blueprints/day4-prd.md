## prd-01 — Architecture Patterns for LLM Apps

**Meta:** evolving/mixed · diff 3 · 240 min → 5,000–6,200 words · prereqs [api-05, rag-05] · related [prd-04, prd-05, eng-04, eng-05]
**Thesis:** production LLM systems converge on a small set of shapes — gateway-centric sync service, async queue worker, RAG service split, agent runtime, event-driven pipeline — and the architectural decisions (sync/async, state placement, multi-tenancy, scaling unit) follow from workload shape plus the three costs of fnd-05.
**Sections:** (1) Intuition: LLM calls are slow, expensive, stateful-per-request (KV), and fallible — every architecture pattern is a response to one of those four facts. (2) The shape catalog (compose from eng-05's patterns, teach the decisions): sync request/response behind the gateway (interactive, streaming — api-05); async queue worker (long tasks, agents, retries decoupled from user connections — when P99 generation exceeds HTTP patience); the RAG split (eng-01's two-system view generalized: latency path vs batch path); the agent runtime as a job system (eng-02: checkpointable, resumable, budgeted); event-driven enrichment (documents in → enriched out — batch API native). (3) Cross-cutting decisions: state placement (conversation state stores, rag-01/agt-04 applied at infra level), multi-tenancy (per-tenant keys/quotas/indexes — blast radius + noisy neighbors + data isolation per sec-03), queue design for LLM work (priority lanes: interactive vs batch; token-aware rate shaping — api-01's TPM math as queue policy). (4) Scaling units: what actually scales (stateless app tier trivially; the model tier by provider quota or GPU count — prd-06; the index tier per rag-03); the bottleneck-finding discipline. (5) Worked example: evolve one product (the capstone) v0 monolith → v1 gateway+queue+RAG split → v2 with routing/fallbacks — each step triggered by a named, measured pain.
**Must land:** architecture follows workload shape (api-05's classification, promoted to system design); async-by-default for anything over ~10s; multi-tenancy is a day-one decision (retrofits are migrations); evolve by measured pain, not by pattern-collecting (fnd-01's premature depth).
**Diagrams:** (1) *graph TD* the shape catalog with selection criteria; (2) *graph LR* the v0→v1→v2 evolution of the worked example.
**Mini-project:** re-architect the capstone on paper per the worked example: identify its current shape, its next measured pain, and the v1 diagram; implement the one change that pain justifies (likely the async path for long tasks). Success: an architecture decision traceable to a measurement. Capstone: the capstone's production architecture doc.
**Sources:** [T3] Kleppmann, *Designing Data-Intensive Applications* (queue/state fundamentals) · [T4] Anthropic building-effective-agents (runtime shapes) · [T1] provider streaming/batch docs (reuse api-05's) · [T2] Kwon PagedAttention arXiv:2309.06180 (why the model tier is special, reuse).
**Volatile fences:** none heavy; this is the module's most stable chapter.

## prd-02 — Inference Internals & Serving

**Meta:** evolving/mixed · diff 5 · 300 min → 6,200–7,000 words · prereqs [fnd-05, api-07] · related [prd-03, prd-06, eng-08]. **The module's flagship — the fnd-05 treatment for serving.**
**Thesis:** serving LLMs is a memory-bandwidth-and-scheduling problem: continuous batching keeps GPUs saturated across requests, PagedAttention manages KV memory like virtual memory, and the prefill/decode asymmetry (compute-bound vs bandwidth-bound) drives every optimization and metric in the serving stack.
**Sections:** (1) Intuition: a GPU serving one request at a time idles ~90% of its compute during decode (bandwidth-bound — fnd-05); serving engineering is the art of filling that idle capacity with other requests' work. (2) The two phases, at systems depth (fnd-05 recap → operational): prefill (parallel, compute-saturating, TTFT) vs decode (sequential, bandwidth-bound, TPOT); why they fight when co-scheduled (a long prefill stalls everyone's decode — the latency-spike mechanism); chunked prefill as the truce. (3) Continuous batching: static batching's waste (batch waits for the slowest) → iteration-level scheduling (requests join/leave the batch each decode step — cite Orca); the throughput/latency dial (batch size ↑ → throughput ↑, TPOT ↑). (4) KV memory management: PagedAttention as virtual memory for the cache (blocks, no fragmentation, sharing for common prefixes — cite Kwon; this is where api-05's prompt caching physically lives); prefix sharing, eviction policies, preemption under pressure. (5) Serving metrics and tuning: TTFT / TPOT / goodput (SLO-meeting throughput — the honest metric); the tuning workflow on vLLM-class engines (max batch, KV budget, chunked prefill knobs) benchmarked on YOUR traffic shape (api-07's rule); disaggregated prefill/decode as the frontier (separate fleets per phase — cite DistServe; fence as evolving). (6) Napkin math throughout: tokens/sec ceilings from bandwidth (params × 2 bytes ÷ bandwidth = per-token floor), concurrency from KV budget (fnd-05's formula ÷ per-request cache).
**Must land:** decode is bandwidth-bound (the single most explanatory fact in serving); continuous batching is why providers are cheap and your naive self-hosting isn't; PagedAttention = virtual memory (the analogy teaches itself); goodput > raw throughput; benchmark on your traffic shape.
**Math that earns its place:** bandwidth-floor tokens/sec; KV-per-token (reuse fnd-05); concurrency ceiling. The chapter's signature numbers.
**Diagrams:** (1) *gantt* continuous batching — interleaved requests across decode steps (the justified gantt from AUTHORING_GUIDE); (2) *graph TD* PagedAttention block mapping (logical KV → physical blocks, shared prefix marked).
**Mini-project:** stand up vLLM on your api-07 model; benchmark tokens/sec and TTFT at concurrency 1/8/32 with your capstone's real prompt shapes; compute the bandwidth floor and compare; toggle chunked prefill and observe the TTFT/TPOT trade. Success: measured curves that match (or interestingly miss) the napkin math. Capstone: the capstone's self-hosted route, properly served.
**Sources:** [T2] Kwon et al., PagedAttention, arXiv:2309.06180 · [T2] Yu et al., Orca (OSDI 2022) · [T2] Zhong et al., DistServe, arXiv:2401.09670 · [T2] Dao FlashAttention arXiv:2205.14135 (reuse) · [T1] vLLM docs (serving args, metrics) · [T1] NVIDIA GPU memory-bandwidth specs page (for the napkin constants).
**Volatile fences:** engine features and knob names; the physics and scheduling concepts are stable.

## prd-03 — Inference Optimization

**Meta:** evolving/mixed · diff 5 · 240 min → 5,000–6,200 words · prereqs [prd-02] · related [ftn-06, api-07, eng-10]
**Thesis:** the optimization toolkit — quantization, speculative decoding, distillation, attention/kernel efficiency — attacks either the memory-bandwidth wall or the sequential-decode floor identified in prd-02; each technique is a quality trade measured on your eval (api-06 discipline), never a free lunch.
**Sections:** (1) Intuition: prd-02 gave two enemies — bytes moved per token (bandwidth) and one-token-per-step (sequentiality); every technique here attacks one of them; name which, always. (2) Quantization at depth (api-07 recap → mechanics): weight-only (GPTQ/AWQ-class: calibration, group size, outlier handling — why naive rounding fails and activation-aware works) vs weight+activation; KV-cache quantization (attacks the other memory consumer — fnd-05); the eval-per-level doctrine (every bit-width is a model version — api-07); where quality falls off (precise reasoning, long-tail — fnd-09's shallows degrade first). (3) Speculative decoding: draft-model proposes k tokens, target verifies in one parallel pass (the sequentiality hack — exact output preserved via rejection sampling; cite Leviathan/Chen); the acceptance-rate math (speedup ≈ f(acceptance, k, draft cost) — worked example); self-drafting variants (Medusa/EAGLE-class, one honest paragraph, fenced). (4) Distillation as serving strategy (pointer to ftn-06 for training mechanics): the smallest-model-that-passes-the-eval doctrine; cascade placement (eng-05 #2). (5) The optimization decision tree: symptom (TTFT / TPOT / cost / capacity) → technique; compounding order (quantize first — cheapest; speculate second; distill third — most effort) and their interactions.
**Must land:** name the enemy (bandwidth vs sequentiality) before choosing the weapon; speculative decoding is exact (no quality trade — the rare free-ish lunch, paid in draft-model serving); quantization quality loss is task-jagged (fnd-09); the eval decides every level.
**Math that earns its place:** speculative speedup formula with acceptance rate; quantized-bytes bandwidth floor (extends prd-02's).
**Diagrams:** (1) *graph LR* speculative decode round: draft k → parallel verify → accept/reject; (2) *graph TD* the symptom→technique decision tree.
**Mini-project:** on the prd-02 setup: quantize to two levels and re-run the capstone eval + tokens/sec (the api-07 bake-off, deepened); if the engine supports it, enable speculative decoding and measure acceptance rate + speedup on your traffic. Success: a quality/speed frontier plot for your own model. Capstone: the self-hosted route optimized, with evidence.
**Sources:** [T2] Frantar et al., GPTQ, arXiv:2210.17323 · [T2] Lin et al., AWQ, arXiv:2306.00978 · [T2] Dettmers LLM.int8 arXiv:2208.07339 (reuse) · [T2] Leviathan et al., speculative decoding, arXiv:2211.17192 · [T2] Chen et al., speculative sampling, arXiv:2302.01318 · [T1] vLLM quantization/spec-decode docs.
**Volatile fences:** method landscape (heavy — quant/spec variants churn); the two-enemies frame and eval doctrine are stable.

## prd-04 — Reliability Engineering

**Meta:** evolving/mixed · diff 3 · 180 min → 4,300–5,000 words · prereqs [api-05, evl-04] · related [prd-01, eng-05, eng-08]
**Thesis:** LLM reliability extends classic SRE with one novel failure class — quality brownouts (the service is up, the answers got worse) — so the toolkit is retry budgets, fallback chains, load shedding, and timeouts sized to token budgets, plus online quality monitoring as a first-class SLI.
**Sections:** (1) Intuition: provider failures are weather (api-01) — reliability engineering is dressing for it; the SLO set for LLM systems: availability, latency (TTFT/total, per stage — eng-01), and *quality* (the new one — judge-sampled, evl-05). (2) The failure taxonomy with responses: hard failures (429/5xx/timeouts → api-01's retry discipline, matured: budgets, jitter, circuit breakers — a tripped breaker fails fast to fallback instead of queueing doom); latency degradation (P99 blowups → hedged requests for idempotent short calls, honest cost note; timeout hierarchies sized to max_tokens — api-01); capacity exhaustion (load shedding by priority lane — interactive sheds last, batch first; prd-01's queue design pays here). (3) Quality brownouts (the chapter's signature section): silent provider-side changes (fnd-07 drift, serving changes under a pinned alias), detection via online judge sampling + refusal/format-rate alarms (evl-05, eng-04's dashboard rows), response: pin audit → canary rollback → provider escalation with evidence from traces. (4) Fallback chains at depth (eng-05 #3 taught): design (same-provider smaller model vs cross-provider vs cached/static), the quality-vs-availability trade per route, eval-baselined fallbacks, *exercised* quarterly (trickle traffic — an untested fallback is decorative), and the cross-provider portability tax (api-06). (5) Degraded modes as product design: what the user sees during each failure class (honest unavailability vs silent quality drop — pick honesty); graceful-degradation ladders (full RAG → cached answers → "try later").
**Must land:** quality is an SLI (the LLM-specific insight); retry storms are self-inflicted (budgets + jitter + breakers); fallbacks are eval-baselined and rehearsed; degradation is a product decision made before the incident.
**Diagrams:** (1) *stateDiagram-v2* circuit breaker with fallback chain; (2) failure-class → response table.
**Mini-project:** harden the capstone gateway: circuit breaker + one eval-baselined fallback (smaller model), chaos-test by injecting 429s/timeouts, and add a judge-sampled quality alarm; run a game-day exercising the fallback. Success: a survived synthetic outage with measured user impact. Capstone: the capstone survives its first game day.
**Sources:** [T3] Google SRE Book (free online — breakers, shedding, SLOs) · [T1] provider error/rate-limit docs (reuse api-01's) · [T1] provider status-page history (incident reality) · [T2] Zheng judge arXiv:2306.05685 (quality sampling, reuse).
**Volatile fences:** provider SLA specifics; the taxonomy and brownout doctrine are stable.

## prd-05 — Cost Engineering

**Meta:** evolving/volatile · diff 3 · 180 min → 4,300–5,000 words · prereqs [api-06, prd-01] · related [eng-10, api-05, ftn-06]
**Thesis:** cost is a designed property, not a bill you receive — unit economics (cost per task, margin per feature) drive architecture, and the discipline is attribution, forecasting, and the eng-10 lever catalog applied through evals; this chapter teaches the mechanisms behind eng-10's procedures.
**Sections:** (1) Intuition: tokens are metered compute with 100× spreads across models and 10× spreads across prompt designs — cost variance this wide makes cost a first-class design input (fnd-01's promise, delivered). (2) Unit economics: cost-per-task decomposed (eng-10's formula, derived term by term with the mechanisms: why input/output prices differ — fnd-05; why retries multiply — api-03; why cache share dominates — api-05); margin per feature (cost-per-task vs value-per-task — the conversation with the PM); attribution plumbing (per-route/user/feature tags in the trace store — evl-04). (3) Forecasting: traffic × mix × token distributions; the nonlinearities that break naive forecasts (context growth with adoption — api-01's conversation-bloat curve; agent-step distributions — agt-09; seasonal mix shifts). (4) The lever catalog with mechanisms (eng-10 ordered them; teach *why* the order holds): correctness-free first (caching/batch — no eval risk), then measured-risk levers (output discipline, routing, slimming), then structural (self-host/distill — api-07/ftn-06 TCO); semantic caching's staleness contract at depth (the fnd-03 blind-spot mechanism behind eng-05's caution). (5) The economics conversations: build-vs-buy at the route level, commit negotiations (volume discounts as selection criteria — api-06), and showback culture (teams see their routes' costs — behavior follows visibility).
**Must land:** cost-per-task is the only honest unit (never per-token, never per-request); attribution before optimization (you can't fix what you can't decompose); the lever order is risk-ordered, not size-ordered; forecast the nonlinearities.
**Diagrams:** (1) *graph TD* cost decomposition tree (task → terms → owning levers); (2) the lever/risk/yield table (extends eng-10's).
**Mini-project:** build the capstone's cost model from its evl-04 traces: cost-per-task per route, attributed and trended; forecast next quarter under 3× traffic with context growth; apply the top two levers from the audit and measure. Success: a defended forecast and a measured lever yield. Capstone: the capstone's unit-economics dashboard (eng-10's audit, automated).
**Sources:** [T1] provider pricing pages (the volatile constants) · [T1] batch/caching docs (reuse api-05's) · [T2] Kwon PagedAttention (serving-cost mechanics, reuse) · internal: eng-10 (the procedure doc this chapter explains).
**Volatile fences:** all prices and ratios (heavy); the decomposition, attribution, and lever-ordering logic are stable.

## prd-06 — Deployment & Infrastructure

**Meta:** evolving/volatile · diff 4 · 240 min → 5,000–6,200 words · prereqs [prd-02] · related [api-07, prd-03, eng-08]
**Thesis:** the compute layer under self-hosted inference — GPU classes, procurement models, autoscaling around cold starts, and capacity planning from the prd-02 math — is where infrastructure instincts need recalibrating: the workload is memory-bound, the "instances" cost five figures a month, and scale-up takes minutes, not seconds.
**Sections:** (1) Intuition: LLM serving inverts web-tier assumptions — vertical beats horizontal until it can't (one big-memory GPU > shards), utilization is the whole economics (api-07's TCO), and elasticity is fought by physics (weights take minutes to load). (2) The hardware landscape (fence hard): GPU memory classes as the real taxonomy (consumer 24GB / prosumer 48GB / datacenter 80GB+ — map to the api-07/fnd-05 sizing math), bandwidth as the throughput ceiling (prd-02), interconnect only at multi-GPU (tensor parallel — when models exceed one device); the honest "read the current spec sheets" posture. (3) Procurement models with break-evens: cloud on-demand (spiky, expensive) → reserved/committed (the utilization bet) → GPU-specialist clouds (price/availability trade) → serverless GPU (per-second billing, cold-start tax) → owned metal (the full api-07 ops product); the decision follows measured utilization, always. (4) Autoscaling reality: cold starts = weights loading + engine warmup (minutes — architect around it: warm pools, scale-up-ahead on forecast, scale-to-zero only for dev/batch); queue-depth-based scaling beats CPU metrics (the right signal is tokens queued — prd-01's queues); multi-region as data-governance topology first (sec-03), latency topology second. (5) Kubernetes + GPUs in one honest section: device plugins, node pools, bin-packing pain, when K8s earns it (existing platform team) vs managed inference services (most teams); capacity planning as the prd-02 worked example × growth forecast (prd-05), with the fleet dashboard (utilization, queue depth, KV pressure — extends eng-04).
**Must land:** utilization is the economics (measured, not hoped — api-07's most-overestimated number); cold starts reshape architecture (warm pools, not autoscaling faith); memory class picks the GPU, bandwidth picks the throughput; procurement follows measured utilization curves.
**Diagrams:** (1) *graph TD* procurement decision tree (utilization × governance × team → model); (2) *graph LR* the scaling pipeline: forecast → warm pool → queue-depth scaler → fleet.
**Mini-project:** capacity-plan the capstone's self-hosted route on paper: from prd-02's measured curves + prd-05's forecast, size the fleet at two procurement models and compute break-even utilization; then measure one real cold start (weights-load to first-token) and design the warm-pool policy it implies. Success: a costed capacity plan with a measured cold-start number. Capstone: the capstone's infrastructure plan, board-presentable.
**Sources:** [T1] NVIDIA datasheets/docs (memory/bandwidth constants) · [T1] vLLM production/distributed docs · [T3] Google SRE Book (capacity planning, reuse) · [T2] DistServe arXiv:2401.09670 (fleet-shape frontier, reuse) · [T1] one serverless-GPU provider's cold-start docs (exemplar, fenced).
**Volatile fences:** the entire hardware/procurement landscape (heaviest in the module); the sizing math, utilization economics, and cold-start doctrine are stable.
